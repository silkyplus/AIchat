# 15.2 在线单聊性能基线

本模块复用C++ ChatBench，增加三个隔离拓扑、实际节点归属核对和重复实验报告。不修改聊天业务、线程数或密码验证。压测准备、账号注册和登录不计入聊天测量。

## 用户运行

```bash
cd /home/chaoqiang/software/chat/CHAT
cmake -S . -B build
cmake --build build --target ChatBench -j2
./deploy/bench/run-baseline.sh
```

默认10对用户，即20个已登录连接；每对正式100条、预热5条，正文128字节。每个拓扑重复3次，共9次正式实验，每次预期1000条唯一投递。屏幕打印PASS、吞吐和投递P95，结束打印Reports目录。

先快速验证可运行：

```bash
python3 tests/bench_baseline_test.py --pairs 3 --messages 20 --repeats 1
```

该场景每个拓扑60条消息，只用于冒烟，不用于容量判断。指定不同消息大小或增加并发：

```bash
./deploy/bench/run-baseline.sh --pairs 10 --messages 100 --bytes 1024 --repeats 3
./deploy/bench/run-baseline.sh --pairs 50 --messages 100 --repeats 3
```

建议先完成默认场景，再逐级增压。参数上限pairs=100、messages=10000、总正式样本200000、bytes=4096、repeats=10。正文下限64字节。运行前检查文件描述符上限；每阶段最大60秒、单消息超时10秒；超过限制如实失败并停止后续实验，不自动继续增压。登录准备等待就绪的编排上限60秒，C++收到ready后等待归属核对放行上限10秒，单次子进程完成等待上限140秒。

## 三种拓扑

| 名称 | 连接方式 | 验证条件 |
| --- | --- | --- |
| single_direct | 收发双方都直接连接节点A | 所有账号server_id为A，所有对为local |
| redis_direct | 每对发送者直连A，接收者直连B | 每对均跨节点，ACK必须submitted_remote |
| nginx_entry | 所有连接经过独立Nginx入口，轮询策略 | 按实际server_id分成local/remote，分别报告 |

单节点阶段只启动A；双节点阶段再启动B。三个拓扑使用同一批独立账号、相同并发与消息大小；每次等待账号离线后重登。Redis始终为独立实例，MySQL使用既有chat_module_test，日常后台进程仍可能争抢同一VM资源，环境中明确注明。

Nginx场景通过connection_order改变连接建立顺序，让3对及以上时同时包含同节点和跨节点样本；这一顺序只构造实验条件，归属判断仍取真实数据库。1或2对不保证混合路由。由于入口场景包含混合路径，不可将其总吞吐直接与全跨节点场景视为等价负载，也不能据此计算纯Nginx开销。

## 关键实现

ChatBench新增每账号可选host/port，支持两端分别直连不同节点；connection_order是账号数组下标的完整排列，建立连接后恢复原来的收发配对，避免更改顺序破坏配对。

新增可选ready_file/start_file握手：

1. C++完成所有登录，原子写出ready文件，保持连接等待。
2. Python查询User的id/state/server_id，核对全部账号在线、归属于测试节点，并检查直连场景的预期节点。
3. 按每对账号实际归属生成local/remote数组，原子写入start文件。
4. C++收到放行后预热并正式测量；对成功ACK同时检查status是否与归属匹配。

查询与握手位于测量之前，不把SQL核对时间混入消息延迟。不携带用户密码到ready/start或结果报告。未启用握手的15.1接口保持兼容，归类为unclassified。

phase按路由分别收集ACK与实际投递延迟，measurement.by_route输出每类sent、ack_ok、received_unique、投递吞吐及延迟分位数。分类吞吐分母统一使用整轮测量时间，代表本轮贡献，不是各类独立跑满的最大吞吐。总体正确性仍检查全部ACK、唯一投递、缺失、重复和未知消息。

C++工具保持每对一条在途、等待ACK和实际接收双条件的闭环模式。时钟为steady_clock，P50/P95/P99为nearest-rank。延迟从发送端排队前到工具观察完整ACK/消息，可能包含压测端调度开销。

## 报告与清理

每次运行目录：`.runtime/bench/baseline-<run-id>/`。

- `summary.md`：每轮结果、各拓扑成功次数、成功轮吞吐中位数和最小/最大值。
- `results.json`：全部已收集结果，保留失败轮和中止原因。
- `<topology>-<repeat>.json`：原始C++计数与总体/分类延迟，附实际owners和节点数。
- `environment.json`：参数、平台、CPU数量、FD上限、CMake配置摘录、服务和工具二进制SHA256、测试节点ID和端口。
- 节点、Redis、Nginx与压测客户端日志；ready/go文件不含密码。

仅成功轮参与中位数汇总，但失败数量保留，不能只引用成功轮掩盖失败。没有成功样本时显示空值。失败也输出报告目录；异常出现后请先检查对应JSON的error和日志。

Python只做隔离服务编排、账号准备、归属核对和汇总，真正并发收发由C++执行。节点使用唯一ID/频道前缀，Nginx运行目录和端口独立。临时账号配置权限0600，用后删除；finally清理自己的服务和账号，不停止日常16014/16015/16016，不清空系统Redis或全表更新在线状态。Ctrl+C会进入清理；强制杀死编排进程不保证清理。

## 数据如何理解

本次是固定消息数、闭环、有限样本基线，不是持续定速压测或最大并发证明。低延迟场景运行可能很短，启动和调度波动影响结果；正式分析应增加消息数并重复，仍保持相同参数对比。群聊、离线存储、CPU/RSS采样和瓶颈归因不属于本模块，留给15.3/15.4。

单节点4个Muduo IO线程，双节点共8个，节点数量与总线程资源不同；服务端、数据库、Redis、Nginx与压测端共享一台VM，不能由此宣称双节点线性扩展。当前构建沿用项目配置，不静默切换Release或关闭日志。二进制SHA256和CMake摘录用于标记实际测试版本。
