# 模块16：数据库连接复用与实测优化

## 解决的问题

原来每个数据模型方法都构造一个 MySQL 对象，调用 mysql_real_connect，执行 SQL，再通过析构 mysql_close。跨节点单聊每条消息查询目标用户状态；群聊每个请求查询成员列表；离线投递还会查询状态并插入消息。这些调用在业务回调中同步执行。连接池把物理连接生命周期从一次模型调用延长到整个服务进程，并保留模型调用的独占租约。

## 16.1 耗时定位

CHAT_DB_PROFILE=/绝对路径/node-%p.json 开启聚合统计，%p 替换进程 PID；正常退出时写文件。不开启时不累加统计，不记录 SQL、消息或密码。目录须预先存在。

- connect：实际 mysql_init/options/mysql_real_connect 次数和累计耗时。
- acquire：获取连接的累计耗时，包含新建连接或池满等待；与 connect 存在包含关系，不能相加。
- sql：mysql_query 调用次数与累计耗时，不包括 mysql_store_result、行解析和 Redis。

统计范围是整个进程，包含启动、注册、登录、预热、正式发送和退出清理。多线程累计时间不能直接等同于墙钟时间。此次连接耗时已能支持连接复用优先级；Redis 内部耗时没有单独测量，不据此判断 Redis 瓶颈。

## 16.2 连接池设计

实现位于 include/server/db/db.hpp 和 src/server/db/db.cpp，模型接口及 JSON 协议不变。

1. 一个进程一个池，默认上限8，按需创建，不会一启动就创建8个连接。
2. connect() 优先取空闲连接；没有空闲且未达上限，先占一个创建名额，再在锁外连接数据库。
3. 已达上限时用条件变量等待，最长3秒。超时返回明确错误，不无限等待。
4. 一个 MySQL 对象独占一个连接；事务里的多条 SQL 始终使用同一个连接，不会交叉使用。
5. 对象析构时，未结束的 START TRANSACTION/BEGIN 事务先回滚，再归还连接。模型目前仅使用这些显式事务语句，不使用自定义会话变量或临时表。
6. 连接级错误（客户端错误码>=2000）或结果读取错误标记坏连接，归还时关闭并释放名额。新租约可重新建立连接。
7. 不自动重放失败 SQL，避免断线时重复插入、重复提交。不保证闲置连接永不断开：第一次发现断线的请求可能失败，后续租约重建连接。
8. 物理连接设置连接、读、写超时各3秒，字符集 utf8mb4。池等待和数据库操作仍同步占用业务线程；本模块不包含异步数据库改造。

配置在进程生命周期内保持不变：

| 环境变量 | 含义 |
| --- | --- |
| CHAT_DB_POOL | 默认1启用；0关闭，保留逐次连接路径用于对比 |
| CHAT_DB_POOL_SIZE | 1～64，默认8，每个服务进程单独计算 |
| CHAT_DB_PROFILE | 可选的正常退出统计文件路径 |

日常已经运行的旧进程不会因重新编译自动升级，需按原部署脚本重启后才使用新代码。本次测试只启动、终止独立测试子进程。

## 实测结论（2026-10-12）

定位与多场景对比：`.runtime/module16/comparison-9e39dd8b1c3d`。每种模式各3轮，12个子任务全部业务验证成功；每轮群聊包含离线记录核对和拉取后数据库清空验证。第一轮关闭连接池的群聊在功能回归结束后补跑，以 jobs.json 中替代后的路径为准，原报告仍保留。最初汇总对离线存储误选无样本的投递延迟字段，已修正为 ACK 延迟并使用 --report-only 重新汇总，无需重跑有效业务观测。

定位样本：发送节点关闭池时 connect 5252次、累计27492ms，mysql_query累计1110.15ms；开启池时仅新建4个连接，累计33.91ms，同样5252次租约获取。此为整个进程的累计计时，不是正式阶段的端到端延迟。

为避免只依赖短窗口，又用最终二进制补充跨节点长样本：`.runtime/module16/comparison-16141dd3c10a`，关闭数据库计时、开启200ms资源采样。10对用户，每对2000条、消息128字节，每种模式重复3轮并交替顺序。每轮20,000条，六轮共120,000条，ACK和收件数量均准确，无缺失/重复；清理无错误，所有正式资源窗口均非短窗口。

| 投递次数/秒 | 575.03 | 8246.17 |

吞吐约14.34倍。CPU秒表示完成相同工作量的累计CPU消耗；MySQL是共享进程，其数据不能完全排除后台负载影响。关闭池单轮约34.7秒，开启池约2.2～2.5秒。同一虚拟机、闭环并发10对、当前数据库和构建配置下成立，不能推广为生产容量或所有场景都提升14倍。本地单聊吞吐基本持平，符合原有本地快路径不查数据库的设计；群聊与离线存储也观察到改善，但部分优化后样本不足1秒，不用它们宣称稳定容量。

## 学习时如何理解

MySQL类现在相当于一个“借用凭证”。构造时还没有连接，connect()向池借用，query/update在独占连接上执行，析构自动归还。这就是RAII：让C++对象的作用域管理资源，异常返回也能执行析构。

mutex保护空闲连接列表和total计数；condition_variable在没有可借连接时释放锁并睡眠，连接归还后notify_one唤醒等待者；谓词在唤醒后重新检查条件，处理虚假唤醒。创建连接在池锁外执行，避免一个慢连接阻止其他线程归还或获取连接。

事务不会在每条SQL后归还连接，而是在整个MySQL对象结束后归还，所以START TRANSACTION、INSERT、COMMIT落在同一个数据库会话。未提交事务析构回滚，防止下一位借用者继承前一位的事务。当前模型不使用其他会话状态；如果未来增加SET、临时表等，需要扩展归还时的会话清理。

本模块证明的优化点是减少反复建立数据库连接的成本。连接池仍使用同步SQL，并不会自动把数据库操作变成异步，也没有修改Redis消息可靠性语义。
