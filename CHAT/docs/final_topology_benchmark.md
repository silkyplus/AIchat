# 连接池优化后的完整聊天路径补测

## 测什么

补齐已上传模块16版本经过Nginx入口的聊天业务数据。ChatServer业务源码和二进制不变，使用与模块16报告一致的服务器SHA256：`663bbf58a5313d35a6ac81c91948b64ce6cc2a92a2f99de4c9bbd7889e24cb9b`。

所有节点启用MySQL连接池，每进程上限8；每个节点仍为1个主EventLoop、4个I/O线程。Redis使用独立测试实例，MySQL使用共享的隔离课程测试库。Nginx为1个worker、stream等权轮询，配置与现有部署模板一致。只创建/停止测试自己的节点、代理和Redis，不重启日常服务。

## 五条路径

| 标识 | 请求路径 | 节点分布 |
| --- | --- | --- |
| single_direct | 客户端直连单节点，本地单聊 | 全部用户在A，作为历史单机参考 |
| local_direct | 客户端直连两节点，各聊天对在同一节点 | 一半聊天对在A，一半在B |
| redis_direct | 客户端直连两节点，Redis跨节点转发 | 每对发送/接收用户分属A/B |
| nginx_local | 客户端均连接Nginx，每对用户分到同一节点 | 一半聊天对在A，一半在B |
| nginx_remote | 客户端均连接Nginx，每对用户分到不同节点 | 每对发送/接收用户分属A/B |

Nginx按连接分配，不按用户关系分配。测试通过顺序建立并登录连接构造预期路由：纯跨节点按发送/接收相邻建连；纯本地每两对按发送1、发送2、接收1、接收2建连。正式发送前读取数据库的server_id确认实际路由；纯本地再检查两个节点的用户数严格相等。C++负载工具同时校验聊天ACK状态与实际路由一致。不能仅凭连接顺序认定成功。

隔离Nginx影响时，应比较local_direct与nginx_local，或redis_direct与nginx_remote；single_direct只有一个聊天节点，不能独自作为代理开销的对照。

## 条件与方法

- 10对、20对用户，即20/40条客户端长连接。
- 消息正文128字节；JSON协议及换行等额外字节不包含在这128字节中。
- 每对同一时刻一个待完成请求，ACK和收件通知均到达后再发下一条。
- 每配置每轮预热50条/对，准备、预热与正式测量分开。
- 先每对500条预跑，按较快路径估算正式样本数，目标8秒。相同并发下三个本地路径使用相同消息数量，两个跨节点路径使用相同数量；每对不超过10000条、每轮不超过200000条。
- 每个配置正式重复3轮；每轮重建独立服务与账号，适当旋转后续路径顺序。
- 200ms CPU/RSS/FD采样，C++阶段事件确认边界；数据库详细耗时统计关闭。
- 吞吐按实际收件消息数/正式阶段秒数；ACK与投递延迟分别记录；P95汇总取各轮P95的中位数。
- 必须检查发送、ACK、收件预期数量一致，无缺失、重复或未知消息；清理失败与采样错误均不能被忽略。

本次使用的本地补测命令（编排脚本保留本地，此次仅上传测试结果）：

```bash
cd CHAT
python3 tests/bench_final_topology_test.py
```

该脚本使用现有C++ ChatBench，仅扩展Python编排中的纯本地/纯跨节点路由与每路径样本数；未改动聊天服务器或C++压测算法。

原始报告在 `.runtime/bench/final-topology-随机ID/`：`results.json`保留预跑与正式子任务目录以及正式观测，`summary.json`/`summary.md`为结果汇总，每个baseline子目录有节点日志、Nginx配置、所有权与逐阶段资源数据。账号配置为临时0600文件，任务完成后删除，不纳入文档或源码。

## 解读限制

闭环、同一虚拟机、共享MySQL、单一消息长度的有限工作量测试，不等于最大容量或生产承诺。客户端CPU接近100%时，负载生成器可能限制吞吐。代理路径在少量轮次中略高于直连，不能据此宣称Nginx加速了聊天服务；应结合波动范围和CPU观察。正式窗口若因样本上限不足5秒，将明确标记，不隐去。

本次结果用于聊天业务路径比较，与网络模型纯回显实验的十几万次/秒口径不同。


## 正式结果（2026-10-12）

| 路径 | 10对：条/秒 | 10对：P95 ms | 20对：条/秒 | 20对：P95 ms |
| --- | --- | --- | --- | --- |
| 单节点直连·本地单聊 | 18,309 | 0.63 | 19,397 | 1.11 |
| 两节点直连·本地单聊 | 17,350 | 0.66 | 18,288 | 1.13 |
| 两节点直连·跨节点单聊 | 8,618 | 1.83 | 10,179 | 3.42 |
| Nginx入口·本地单聊 | 16,663 | 0.78 | 18,006 | 1.35 |
| Nginx入口·跨节点单聊 | 8,737 | 1.85 | 9,818 | 3.35 |

30组正式观测，发送/ACK/收件均为3,275,460条；缺失、重复、未知消息及ACK失败均为0。正式窗口5.44～9.19秒，均超过5秒；360条Nginx客户端会话日志均为status=200。8个预跑/正式子任务全部正常结束，无账号/进程清理错误。原始报告：`.runtime/bench/final-topology-1cd23832f978/`，便于展示的汇总与各轮数据：`docs/benchmarks/final-topology.json`。

同一并发档下，本地直连与Nginx本地使用相同消息数量和两节点均衡分布；跨节点直连与Nginx跨节点也使用相同消息数量。10对时本地每对10000条、跨节点7627条；20对时本地每对7948条、跨节点4060条。正式数据与预跑分开，不混合取中位数。

10对用户下，Nginx跨节点与直连中位数接近（8737与8618条/秒），不能认定代理带来加速；20对下，Nginx跨节点9818条/秒、直连10179条/秒，也应结合波动解读。本地单聊的客户端CPU约91%～99%（100%=一核），负载生成器可能已限制吞吐。跨节点经过Nginx的客户端CPU在10/20对时约64%/74%，这仍是选定负载下的观察，未寻找最大容量。

完整路径结论可以表述为：“在同一虚拟机、128字节正文、20对用户闭环单聊条件下，经Nginx入口的跨节点投递吞吐中位数约9818条/秒，投递P95约3.35ms；三个正式轮次完成243600条跨节点消息，数量与内容校验通过。”不要把本地路径18006条/秒与跨节点9818条/秒混为同一种负载，也不要拿此结果和纯回显实验直接比较。

ChatServer与ChatBench二进制哈希均与模块16原有报告相同；只扩展Python测试编排，没有更改已上传聊天业务。构建沿用原有默认配置，未额外切换Release。此次仅上传本报告、结果JSON及README汇总；测试编排脚本保留本地。
